3Architecture

There are three layers, and the code keeps them from calling each other. The research factory creates and backtests ideas. The league and ranking paper-trade and score them. Capital deployment trades only through the risk and execution layer. The research code cannot import the broker; a regression test enforces this.

Design rules that bear load

  • Fail closed on unknowns. An unknown market cap, liquidity or correlation blocks a trade; it is never treated as average.
  • Append-only records. Strategy identity and version (league.py contains no UPDATE), decisions, the trial counter and accounting. Restatements sit beside originals with an accounting version.
  • Risk limits live apart from strategy config. config/risk.yaml is separate so that a strategy edit cannot widen a limit. LIVE is armed by one line there, and changing it is the owner's step.
  • Idempotency. signal_id is a content hash; broker orders carry a ref_id; after a restart the ledger is rebuilt from the orders table.
  • Broker is authoritative. Every LIVE run reconciles the slot log against Robinhood positions and halts on any difference.
  • Forward genomes stored inline as JSON in paper_runs, which is why forward records survived a 2026-09-12 database corruption.

Integrity rules

  • Point in time. Fundamentals become visible only from the first session after SEC acceptance plus a 2-day lag. Market cap = shares from the filing × price on the filing date. Tested: 2 of 20,000 filings were optimistic, and both are SEC data defects.
  • Freshness. The newest completed session is read from a liquid ETF at the source, never from the table being updated. Partial intraday bars are refused. features, daily_fundamentals and prices are checked against each other.
  • Absence is not zero. Missing debt, R&D or EPS stays missing, and any ratio built from it is missing too. Debt is tagged for only 38% of filers, which limits every EV-based metric.
  • Backups. 46 forward and decision tables are dumped nightly to backups/forward.sql.gz, which is committed to git (last run 09-26: 19,423 rows).

6Dead companies (survivorship)

Free price data omits companies that died. In 2008 our database could price only 22.6% of the universe an investor could have known about; by 2024 it could price 83.7%. Rather than wait for paid data (~$270/yr), the project reconstructs the missing companies:

  1. Which companies existed (Layer A): SEC filers, the delisting registry, Internet Archive snapshots of the symbol directory and FinanceDatabase. 7,618 dead companies have no price history.
  2. How each died: exit type (bankruptcy, buyout, SPAC, other) read from SEC filings for 70% of them (dead_evidence.py).
  3. Their price paths (generator v5c): failures copy the final years of 80 real failed companies (70 from our own prices plus 10 hand-checked FINSABER S&P failures), with the measured pre-death drift (−0.516/yr in log terms over 3 years). Buyouts and SPACs copy real donors of their own type. Delisting-day returns are drawn in the Shumway shape.
  4. Their fundamentals: each dead company's own SEC filings, run through the same metric code. Market cap uses the real 10-K price level where one exists (22% of filings); otherwise it uses the synthetic price.
  5. Their trading volume: a model fitted on 228 real dead companies, checked on held-out companies, so the liquidity rules bind on them too.

7Strategies and the ranking

Ranking formula

score = (k × backtest + n × paper) / (k + n), with k = 10 prior trades and n = closed paper trades, both measured as net return per trade. A strategy whose dead-company backtest loses money is out. A strategy with no backtest starts at 0. Slots take the top five tradeable strategies, at most four from one family. A holder is replaced only when a challenger beats it by 0.2 pts per trade, after at least 3 sessions held, with at most 2 replacements a day.

8Live execution

One run of the trader (every 5 minutes, 13:04–20:59 UTC weekdays)

  1. Kill switches checked: data/KILL_SWITCH, daily loss $15 / 15%, drawdown 35%, order throttles (10 a day, 2 per symbol), broker errors, stale data.
  2. Broker positions reconciled against the slot log; any difference halts the run and alerts.
  3. Stop monitor: ATR stop, time limit, take-profit, strategy exit. Risk exits outrank strategy signals.
  4. Empty slots: the holder strategy's current pick is quoted live, and a quote that is stale or outside market hours is refused.
  5. Risk engine: $25 per order and per position, 30% per symbol, 5 positions, market-cap floor, settled cash (T+1), and the PDT limit of 3 day trades in 5 sessions.
  6. LiveBroker: review → place a dollar-based market order → confirm, with a ref_id. An order whose outcome is unknown is recorded as UNKNOWN and never retried blindly. Partial fills are recorded at the filled quantity.
  7. Heartbeat row written; fills and halts sent to Telegram and the desktop.

Broker mechanics that shape the design

  • Dollar orders are market orders only, and only in regular hours. No stop can rest at the broker for equities, so stops are checked every 5 minutes and overnight gaps are unprotected.
  • Crypto orders can carry a resting stop, which the crypto trader uses. It is inert until allow_crypto: true.
  • Settlement is T+1, so a rotation (sell, then buy) cannot complete on the same day.

10Engineering process

  • Roles. The owner sets direction, approves spend and arms live trading. Claude (Anthropic) architects, specifies, reviews and writes the hard parts. DeepSeek implements specified tasks through an orchestrator (ADO) for about $0.01–0.05 per task.
  • ADO rules. A task needs checkable acceptance criteria. The model may write only the files its task names. Nothing merges automatically: review → approve → merge, with the test gate run under the memory cap. DeepSeek defects caught in review this week include a parser that parsed nothing, ISO-versus-YYYYMMDD date comparisons, a bot token written to logs, and an order join that ignored mode.
  • Tests. 95 test files. The gate (run_tests.sh) passed all 94 gated files on 09-26. Regression tests pin fills, the freeze boundary, live paths (stale quote, partial fill, rejected buy, failed stop sell), point-in-time joins and FCF arithmetic.
  • Change control. One commit per change. Paths are added explicitly, never git commit -a. Changes to live trading code go on a branch and the owner merges them (Claude's auto mode refuses to merge them). The database and its WAL are never versioned.
  • Records. CLAUDE.md holds the project brief and session handoffs. docs/ROADMAP_INTEGRATION.md holds per-stage status. Addenda A–E are the owner's specifications, stored verbatim.

14Questions for the reviewer

  1. Evidence floor. Should real capital wait for a minimum forward record (for example 10 closed paper trades), or is "top five of a blended score" defensible at $100 scale?
  2. Prior weight. Is k = 10 trades the right weight for a backtest prior, given the defect ledger in §12? Should the prior be shrunk (for example halved, or deflated by the number of trials)?
  3. Synthetic dead companies. Is a tuned synthetic reconstruction acceptable for choosing strategies, or should the ranking gate on the worst case until real delisted prices (~$270/yr) are bought?
  4. Diversity. Should the slot engine enforce return correlation between holders, not just a family cap?
  5. Horizon comparability. How should strategies with 5-day and 60-day holds, and crypto, be put on one scale (per trade, per day, or risk-adjusted)?
  6. Test window. Should the backtest window extend to 2020–2025, with the sealed holdout re-drawn, now that the search is frozen?
  7. Published priors (L4). Should post-publication factor returns feed the ranking as a prior, and at what discount for one-stock, $20 implementation?
  8. Operational risk. Is anything in the execution path (§8) missing for unattended trading on a limited-margin account?
